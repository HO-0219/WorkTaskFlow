# Work Task Flow 보안 점검 및 출시 체크리스트

## 이번 점검에서 적용한 보호 조치

- 그룹 키 생성, 재발급, 삭제 API는 그룹 팀장만 실행할 수 있다.
- 그룹 키는 SHA-256 해시만 DB에 저장하고 원문은 생성·재발급 직후 한 번만 표시한다.
- 그룹 목록 응답에는 그룹 키를 포함하지 않고, 그룹 설정 상세에서만 팀장에게 표시한다.
- 그룹 키 생성·재발급·삭제는 `SECURITY_AUDIT` 이벤트로 기록하며 키 자체는 로그에 남기지 않는다.
- 로그인, 그룹 키 참여, 이메일 인증, 비밀번호 재설정 요청에는 IP·경로 기준 속도 제한을 적용한다.
- 변경 요청과 401·403·429 응답은 요청 ID, 경로, 상태, 사용자 ID, 접속 IP, User-Agent와 함께 감사 로그로 남긴다.
- API 응답에 `no-store`, `nosniff`, 프레임 차단, referrer 및 브라우저 권한 제한 헤더를 적용한다.
- 인증번호와 비밀번호 재설정 링크가 포함될 수 있는 메일 본문은 로그에서 제거했다.
- 감사 로그는 기본적으로 `backend/logs/work-task-flow.log`에 기록하며 크기와 보관 개수를 제한한다.

## 출시 전에 반드시 운영 환경에서 설정할 항목

- `JWT_SECRET`은 충분히 긴 무작위 값으로 교체하고 비밀 관리 서비스에서 주입한다.
- 운영 DB 계정은 root를 사용하지 않고 필요한 스키마 권한만 부여한다.
- DB 연결 TLS, HTTPS, `AUTH_SECURE_COOKIE=true`, 운영 프론트엔드 CORS 주소를 적용한다.
- 로그 파일은 일반 개발자와 웹 서버 프로세스가 임의 수정할 수 없는 중앙 로그 저장소로 전송한다.
- 관리자 알림 기준을 정한다: 반복 로그인 실패, 반복 그룹 참여 실패, 401·403 급증, 429 발생, 팀장 권한 변경, 대량 조회.
- 업무·댓글·프로필 데이터의 백업 암호화, 복구 시험, 보존 기간과 파기 절차를 정한다.
- 개인정보 처리방침에 수집 로그 항목, 이용 목적, 보관 기간, 파기 방법과 처리 위탁 사항을 반영한다.
- 침해 사고 담당자, 증거 보존 절차, 사용자 통지와 관계 기관 신고 절차를 문서화한다. 신고 대상과 기한은 출시 시점의 관련 법령을 법무·개인정보 담당자와 확인한다.

## 남은 우선 개선 과제

1. 현재 브라우저 저장소에 있는 access token을 메모리 또는 더 엄격한 세션 구조로 전환해 XSS 탈취 영향을 줄인다.
2. 단일 서버 메모리 속도 제한을 Redis/API Gateway 기반 분산 속도 제한으로 교체한다.
3. CSP(Content-Security-Policy)는 실제 배포 도메인과 OAuth 흐름을 기준으로 웹 서버에서 적용한다.
4. 의존성 취약점 검사, SAST, 비밀 유출 검사, 컨테이너 이미지 검사를 CI 필수 단계로 만든다.
5. 감사 로그 조회 권한과 로그 위변조 방지, 보존 기간, 자동 삭제 정책을 운영 환경에서 검증한다.

## 로그에 절대 남기지 않을 정보

- 비밀번호, JWT, refresh token, 인증번호, 재설정 토큰
- 그룹 키와 초대 링크 원문
- 업무 본문, 댓글 본문, 이메일 본문
- Authorization, Cookie, Set-Cookie 헤더
