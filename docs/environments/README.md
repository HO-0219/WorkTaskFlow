# Work Task Flow 환경 승급 체계

마지막 검토일: 2026-07-25  
문서 책임자: 미정  
현재 단계: 1단계 로컬 QA

## 단계 정의

| 단계 | 환경 | 목적 | 실제 고객 데이터 | 실제 결제 | 검색 노출 |
| --- | --- | --- | --- | --- | --- |
| 1 | 로컬 QA | 개발자 단위 기능·회귀 테스트 | 금지 | 금지 | 차단 |
| 2 | 로컬 + ngrok QA | 모바일·외부 콜백·HTTPS 테스트 | 금지 | 금지 | 차단 |
| 3 | AWS QA | 배포·Nginx·DB·장애복구 검증 | 금지 | 금지 | 차단 |
| 4 | 도메인 연결 사전 서비스 | 실제 도메인의 전체 사용자 흐름 검증 | 동의한 내부 테스터만 | 테스트 결제 | 출시 결정 전 차단 |
| 5 | 등록 완료 실제 운영 | 일반 고객 대상 유료 서비스 | 허용 | 허용 | 허용 |

각 단계는 이전 단계를 대체하지 않는다. 장애 재현은 1단계, 외부 콜백 확인은 2단계, 배포 검증은 3단계처럼 목적에 맞는 환경을 계속 유지한다.

## 운영 원칙

1. `.env`와 비밀값은 Git에 커밋하지 않는다.
2. 단계별 DB, 업로드 저장소, 메일 발송자, OAuth 앱, 결제키를 공유하지 않는다.
3. 1~4단계에는 실제 카드정보나 일반 고객 개인정보를 입력하지 않는다.
4. 테스트를 통과했다는 이유만으로 다음 단계로 자동 승급하지 않는다. 담당자가 체크리스트와 롤백 방법을 확인한다.
5. 새 기능은 [환경 영향 템플릿](./ChangeImpactTemplate.md)을 작성하고 5개 환경의 변경 여부를 모두 표시한다.
6. 법률·결제·AWS 정책처럼 바뀔 수 있는 항목은 링크와 확인일을 기록하고 운영 전 다시 확인한다.

## 권장 배포 흐름

```text
기능 브랜치
  → 1 로컬 QA
  → 2 ngrok QA (외부 연동이 있을 때)
  → 3 AWS QA
  → 4 도메인 사전 서비스
  → 승인·백업·롤백 확인
  → 5 실제 운영
```

긴급 수정도 가능한 한 같은 흐름을 따르되, 생략한 단계와 이유를 배포 기록에 남기고 운영 반영 직후 생략한 검증을 수행한다.
